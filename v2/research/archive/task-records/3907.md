# Finalize V2 Architecture and Data Plan

## What & Why
Turn the approved V2 server-design basis and owner decisions into an implementation-ready architecture and cutover plan. Verify that Replit can support the proposed API-plus-worker arrangement before V2 feature work begins, and keep all exploration isolated from live V1 data and operations.

## Done looks like
- A reviewed architecture describes the API and worker responsibilities, canonical run and inventory state, idempotent commands, worker ownership, and database connection budgets.
- An isolated feasibility check confirms the proposed Replit API/worker deployment and shared database behavior, or records the exact platform limitation and a revised recommendation.
- The sync design covers multiple devices, wake/reconnect snapshot recovery, read-only offline behavior, and worker restart/retry without duplicate progress.
- A table-level transfer plan carries approved setup/master data and account roles, excludes historical production runs, invalidates old sessions, and seeds V2 inventory from a fresh physical count.
- V1 remains unchanged; there are no production data writes or historical-run imports.
- The document ends with measurable acceptance checks and staged implementation steps for run control, all stations, full inventory, imports, sync, and auto-tracking.

## Out of scope
- Building the V2 production application.
- Changing or migrating the live V1 database or deployment.
- Transferring historical production runs, V1 inventory balances, or inventory movement history.
- Adding native mobile apps or scaling to multiple API/worker instances.

## Steps
1. **Reconcile requirements and current data** — Confirm the approved V2 scope and map the current schema into carry, exclude, and cutover-baseline groups.
2. **Prove the deployment boundary** — In an isolated non-production environment with synthetic data, verify the Reserved VM API and single-worker arrangement, shared database access, restart behavior, and publish compatibility. Record connection ceilings and any unknowns; do not infer capacity from a later sample.
3. **Define server ownership and commands** — Specify run/station/inventory command boundaries, revisions, idempotency keys, manual adjustment conflict behavior, and the worker lease/fencing rules that prevent duplicate automatic progress.
4. **Define device recovery** — Specify canonical snapshot and cursor/outbox behavior, SSE's notification role, multi-device convergence, offline read-only UI, and wake/reconnect adoption before writes resume.
5. **Specify migration and cutover** — Produce an explicit table allowlist, secure account/role revalidation approach with old sessions invalidated, fresh physical inventory count procedure, and V1 history access/retention recommendation.
6. **Deliver the implementation plan** — Add failure cases and acceptance checks for two-device active runs, background/wake, worker restart, offline access, inventory transactions, and imports; sequence the later V2 build into reviewable stages.
