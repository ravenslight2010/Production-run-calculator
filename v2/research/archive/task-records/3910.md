# Preserve Production Data Before VM Switch

## What & Why
Before changing the published app from Autoscale to a Reserved VM, preserve the complete current production dataset in the development database. The owner chose full production records, including operational history and inventory records; V1's earlier V2-only transfer scope does not limit this preservation copy.

## Done looks like
- The exact published production database and development destination are identified, and their schemas are compared before any restore.
- A protected, restorable production backup and a separate backup of the current development database exist before changes.
- A rehearsal restore succeeds against an isolated disposable database before the development database is replaced.
- The complete approved production record set is present in development and verified with table/row counts, integrity checks, key relationships, run history, and inventory-ledger reconciliation.
- Account, role, credential, session, reset-token, audit, and other sensitive tables have an explicit transfer decision; secrets and live sessions are not copied into the development app.
- Production remains available and unchanged until the copy and verification pass; the app is not switched or republished by this task.
- The final snapshot boundary is documented so changes made after the export cannot be mistaken for copied data.

## Out of scope
- Changing the published app's deployment type or taking it offline.
- Writing to or modifying the production database.
- Copying environment secrets, deployment credentials, active sessions, or password-reset tokens.
- Deleting the existing development database or its backup.
- Treating this preservation copy as approval to import historical V1 runs into a separate V2 database.

## Steps
1. **Confirm endpoints and scope** — Identify the exact Replit production database behind the published Autoscale app and the exact development database to receive the copy. Inventory every application table and classify production records, including accounts/roles, operational and audit history, sync state, inventory balances, and inventory movements; document any credential-bearing fields that need a separate decision.
2. **Compare database schemas** — Compare production and development schemas and app revisions. If the development schema cannot safely restore all production records, stop and provide a compatibility plan rather than forcing schema changes or discarding rows.
3. **Protect both databases** — Create a protected production backup and a separate backup of the current development database. Keep dump files and connection strings out of Git, deployment bundles, logs, and ordinary project files; verify backup readability and restore permissions.
4. **Rehearse the restore** — Restore the production backup into a disposable isolated database with the documented PostgreSQL tools and safe restore options. Check extensions, constraints, sequences, foreign keys, and sensitive-data handling before touching the development target.
5. **Prepare the final copy window** — Determine how to capture writes made after the rehearsal/export. Keep the published app online until the owner approves a short final write-pause or an equivalent final snapshot procedure; state the expected user-visible downtime and exact cutoff.
6. **Restore to development with a destructive-change gate** — Back up the destination immediately before restore and obtain explicit confirmation that replacing its current data is acceptable. Restore the full approved production record set; do not run any command against production that writes or drops data.
7. **Verify and hand off** — Compare source/export/destination table counts and integrity checks, reconcile inventory quantities and movement history, verify run and audit history, and test development sign-in without reusing live sessions. Record the source snapshot time, omitted sensitive fields, restore results, and any post-snapshot changes before the owner decides whether to switch deployment type.
