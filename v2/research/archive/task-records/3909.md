# Build run control that stays consistent across devices

## What & Why
The architecture is ready for V2 implementation, but users need a first operational slice that can start, pause, resume, and complete a run without device-local state becoming authoritative. Two devices must converge on the same run, and automatic progress must remain correct when the worker restarts.

## Done looks like
- V2 stores canonical run lifecycle, station progress, server timestamps, revisions, idempotency receipts, and durable worker lease/fencing state.
- The web/PWA can create, start, pause, resume, and complete a run through authenticated server commands.
- Two devices show the same canonical run state; stale replacements receive an explicit conflict and updated snapshot.
- Retrying a command after a lost response returns its prior receipt and never duplicates progress.
- Worker restart before or after commit cannot advance the same due action twice; stale worker generations cannot commit.
- Offline clients display last-confirmed state as stale/read-only and adopt a canonical snapshot before writes resume.
- Automated tests cover two-device command races, wake/reconnect, worker failure, and idle no-work behavior.

## Out of scope
- Full station-by-station implementation, full inventory, workbook imports, historical V1 runs, and V1 production changes.
- Multi-instance API/worker fleets and native mobile applications.

## Steps
1. Complete and pass the isolated Reserved VM pilot before V2 feature coding.
2. Add the canonical run/station command and revision contracts, transactional receipts, audit/outbox, and conflict responses.
3. Implement lease ownership, fencing, and deterministic due-action identity for the single worker.
4. Build the responsive PWA lifecycle controls and canonical snapshot adoption path.
5. Verify two-device, retry, wake, offline, worker-restart, and idle acceptance checks from the architecture.
