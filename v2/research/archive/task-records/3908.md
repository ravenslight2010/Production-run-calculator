# Prove V2 can run safely on an isolated Reserved VM

## What & Why
The finalized architecture found that separate Replit artifacts cannot use independent deployment modes, and separate projects do not share a managed production database. The recommended one-project, one-Reserved-VM setup with supervised API and worker processes has not yet been deployed or tested. This proof is a hard prerequisite to V2 feature work.

## Done looks like
- An isolated V2 project and disposable database run one Reserved VM deployment with one API process and one supervised worker process.
- Both processes read and write the same synthetic database marker; neither process can reach V1.
- Worker-only restart and full deployment restart recover safely; crashes before and after a committed due action produce no duplicate progress.
- A harmless publish confirms process/version behavior and records compatibility results.
- Actual database usable connections and aggregate API/worker/publish pool maxima are measured; configured maxima stay at or below 80% of usable connections with at least 20% headroom.
- Sanitized evidence updates the feasibility matrix and either passes the architecture gate or recommends a revised hosting/database boundary.

## Out of scope
- Publishing or changing V1, connecting to V1 production data, using customer data, or implementing V2 features.
- Assuming separate projects share Replit-managed databases or introducing an external database without approval.

## Steps
1. Obtain access to a separately provisioned V2 Replit project and disposable database; verify their identity before deployment.
2. Configure a single Reserved VM process supervisor for the API and worker; test health and database marker access.
3. Inject worker and deployment restarts before/after transaction commit; verify lease takeover, fencing, and idempotency.
4. Publish a harmless version change and measure the connection ceiling and deployment overlap.
5. Record sanitized results and update the design gate.
