## 1. Live-calc (`@workspace/live-calc`)

### Role
Pure, shared calculation and operational projection used by **web** and **API**. Server SSE ticks and client `LiveRunProvider` should call the same functions so offline fallback matches server authority when connected.

### Major modules (from package exports)
| Module | Responsibility |
|--------|----------------|
| `computeCalc` / `computeServerCalc` | Core production math from form values + run meta + now |
| `applyTemporaryOverrides` | Temp freezer/cycle overrides into effective inputs |
| `autoTrackEngine` | Suggestion, period clamps, claim mutation builders |
| `autoTrackSchedule` | When next case/sauce/app batch is due |
| `wallClockEngine` | Wall-clock bookkeeping, rearm, tick, replay cap |
| `linePhases` | Line phase strips / switchover semantics |
| `operationalRunView` / `operationalProjection` | Server-shaped live view for SSE |

### Design rules
- **Server calc** takes a sync-shaped payload + optional pep types + `nowMs`.
- Web historically had slightly different period clamp defaults than server (`clampWebPeriodMs` vs schedule clamp)—extraction plan requires preserving that split.
- Inventory helpers (`casesOnLine`, `casesInFreezer`) come from `@workspace/inventory-math`.

### Risks / gaps
- Any drift between client-only calc paths and `computeServerCalc` shows up as “tablet disagrees with server” during reconnect.
- Large `CalcFormValues` surface area = payload growth (ties to sync size research).

## 2. Auto-track

### Mental model
Auto-track is **not** continuous inventory writes. It is:

1. **Schedule** — given run timing + calc, when is the next claim due?  
2. **Claim** — idempotent instruction (`eventId`, `generation`, `sequence`, channel).  
3. **Mutation** — field `from` → `to` on run progress registers.  
4. **Optional inventory side-effect** — e.g. sauce-barrel consumption attached to claim while row lock held.

### Channels (`AUTO_TRACK_CHANNELS`)
`case`, `tray-consume`, `tray-produce`, `batch-consume`, `batch-produce`, `hopper`, `sauce-barrel`, `app1-batch`…`app4-batch`.

### Coordination state
Per run, per channel:

```text
generation, sequence, nextDueAt, acceptedEventId?, acceptedRunValuesUpdatedAt?, updatedAt
```

Stored on the day-state document (`autoTrackCoordination`) so peers and server share claim identity.

### Server ticks (`autoTrackServerTicks.ts`)
- Builds schedule via `computeAutoTrackSchedule` / `computeServerCalc`.
- Net channels for sauce + app batches; wall-clock replay capped (`WALL_CLOCK_REPLAY_CAP_MS` = 6h).
- Emits mutations + claims; coordination generation invalidates when progress registers change (pairs with `protectRunValues` coordination rules).

### Client
- `useAutoTrack` / engine extraction into `lib/live-calc` (plan: zero behavior change).
- **Wake fence:** auto-track blocked until foreground recovery acknowledgement (prevents hidden-time claims).
- Manual packaging override: **server-capped** to +60s (cannot suppress forever).

### Risks / gaps
| Risk | Notes |
|------|--------|
| Claim vs stamp race | Claim advances counts; reconnect LWW can still fight if stamps wrong |
| Double claim after wake | Fence + generation designed to prevent; needs soak on real tablets |
| Inventory only on some channels | Sauce barrel consumption typed; full FEFO/lot consumption still product gap |
| Ended-run drain | `allowEndedDrain` option—must not over-claim after stop |

## 3. Import system

### Architecture
- **Parsers** live in workspace libs (`@workspace/spec-import`, premix, cheese, etc.).
- **AI match** is assistive; deterministic path preferred (importer redesign).
- **Corpus harness** re-parses `attached_assets/source-library` against snapshots after importer changes.
- **Web UI:** deferred dialogs (`useHomeImportDialogs`); Home keeps loaders/commit in composition root.

### Plan highlights (`docs/import-system-plan.md`)
Planned / partial: structured preview diff, rollback via undo snapshot, batch multi-file, template download, pre-AI validation, QC approval queue (owned by QC plan—not import phase order).

### Lifecycle
```text
file → parse → match/review → apply → import history + change manifest
```

Apply touches **factory/master data** (profiles, recipes, mixes)—not primarily the live day-state blob. After apply, profile/factory sync paths replicate.

### Risks / gaps
- Apply without preview diff → operator trust issues.
- Rollback vs later second import conflict (plan calls this out).
- AI parse cost/timeouts isolated from sync (server resilience)—keep it that way.
- Identity resolution for ingredients (separate 2026-09-15 doc) affects allergen and inventory later.

## 4. Factory-data sync

### Role
**Facility-wide KV**, not date-scoped day-state.

Pattern (`factoryDataSync.ts`):

1. `GET /api/factory-data` → full keyed map  
2. `hydrateFromServer()` — per-key **stamp compare**; cached keys → localStorage; server-only keys → module state  
3. `putFactoryKey()` — fire-and-forget PUT on local mutation  

### Key classes
| Class | Examples | Storage |
|-------|----------|---------|
| **Cached** | brands, flavors, ingredient lists, recipe names/presets, mergedAway, delete stamps | localStorage cache + server |
| **Server-only** | stop reasons, packaging option lists (circles, shipper, skid stacking, grip sheets) | module state after fetch |

### Properties
- Fail-safe: network/storage errors swallowed → offline continues.  
- Removed from day-state sync payload (reduces PUT size; important for 512KB cap).  
- Configuration invalidation over SSE is a **nudge** (`family: factory-data`), not a full dump.

### Risks / gaps
- Fire-and-forget PUT can lose last write if offline forever—acceptable for lists; bad if treated as compliance evidence.  
- Stamp compare per key is independent of day-state `canonicalRevision`.  
- Startup hydrate race with first import apply—ordering matters.

## 5. Profile sync

### Role
Brand/flavor **profiles** (setup defaults) are **factory-wide**, synced similarly to factory KV (`profileServerSync.ts` is the pattern factory-data followed).

- Not embedded in day-state recipe payload for list transport.  
- Run form still **copies** profile into `runValues` when applying setup.  
- SSE configuration invalidation family includes `profiles`.

### Risks / gaps
- Editing a profile does not rewrite historical runs (by design)—operators may expect “update everywhere.”  
- Profile apply during run switch must respect form handoff fences (home architecture).  
- Concurrent profile edit on two tablets: last PUT wins per key unless server adds stronger versioning.

## 6. Schema (`lib/db`)

### Shape (from schema barrel exports)
Domain tables group roughly as:

| Group | Examples |
|-------|----------|
| **Auth / ops** | users, sessions, roles/capabilities (via routes), audit log |
| **Sync** | `dailySync`, `dataReset`, `syncConflictLog`, operational intent ledger, completed history |
| **Master data** | ingredients, brand profiles, die types, recipes (dough/cheese/sauce), mixes |
| **Import** | saved sheets, import history, aliases, merge aliases, denied merges |
| **Inventory / pulls** | inventory-related, freezer pull/surplus, mix surplus |
| **Quality** | quality checks, field checks |
| **AI** | result cache, conversation turns, corrections, facility knowledge |
| **Jobs** | server jobs, background operations, cache maintenance |
| **Factory** | `factoryKv` |
| **Other** | web push, action items, cycle counts, supervisor PIN, master data health |

### Rules
- Drizzle is source of truth; forward-only; migrate image separate from runtime.  
- Schema-safe rollback rehearsal is a **first-class** release check.  
- Day-state is largely a **JSON document** on `daily_sync`—relational richness is around it (intents, conflicts, factory KV).

### Risks / gaps
- Document growth in `daily_sync.data` vs normalized tables (run_lots, QC)—product evolution tension.  
- Heal/repair jobs can rewrite master data at startup—fingerprint manifests exist for a reason.

## 7. `home.tsx` architecture

### Role
**Composition root**, not source of truth for every state kind (`docs/home-architecture.md`).

| Owner | Responsibility |
|-------|----------------|
| Home | `dayState`, run switch handoff, providers, deferred import surfaces |
| `useHomeRunIdentity` | current run/id + refs |
| `useHomeNavigation` | tabs only—no day-state |
| `LiveRunProvider` | clock, calc, auto-track bookkeeping, live notifications |
| Form lifecycle hooks | identity fence, autosave, heal |
| Sync coordination | SSE, push queue, wake barrier |
| Station tabs/panels | station UI; consume context |

### Change rules (condensed)
- Don’t put per-second clock in non-live shell components.  
- Run switch must settle form before autosave.  
- Sync machine owns ordering; domain policies own merge; adapters own storage records.

### Risks / gaps
- File size (~1.3MB source) → high merge conflict and review cost.  
- New features tend to land in Home; architecture doc exists to push ownership outward.  
- Cross-run contamination guards (form id vs current run id) are critical and easy to break.

## 8. E2E (Playwright)

### Layout
- Multiple configs: main, phone, PWA, visual, photo-count, sync-convergence, department isolation.  
- **Serial** browser for live-day safety (`workers: 1` on full suite).  
- Destructive tests require `E2E_TEST_DB` + `E2E_APPROVED_DESTRUCTIVE_MODE`.  
- Department e2e: `prepare:e2e:department` applies schema on isolated DB then runs API.

### Notable suites
- Sync convergence (browser + API integration counterparts)  
- Phone / real-mobile (needs CDP endpoint)  
- PWA morning / handoff  
- Release-bound smoke and full suite  

### Risks / gaps
- Full suite **~159 cases**, 45-minute hard limit—duration regressions flagged vs prior baseline.  
- Real device floor trials still blocked without endpoint.  
- Flakes vs product fails must stay classified (release evidence distinguishes infrastructure timeout from assertion fail).

## 9. Release evidence system

### Commands
```bash
pnpm run release:check          # standard gates
pnpm run release:check:full     # + full browser suite
pnpm --filter @workspace/scripts run check:release-evidence
```

### Contract
Success = **exit 0** and **retained evidence verifier** for the **same git revision**.

| Concept | Rule |
|---------|------|
| PASS / FAIL | Product or validation outcome |
| INFRASTRUCTURE TIMEOUT / ERROR | Not treated as product pass |
| Missing gate / missing evidence | Incomplete—never a pass |
| Full suite GO | All enumerated cases completed + verifier |
| Duration alert | File ≥30s and ≥25% slower than prior baseline—review signal, not skip |

### Evidence paths
- Standard: `release-evidence/` (smoke, a11y, webkit, logs)  
- Full: `release-evidence-full/` + `browser-full/FINAL-REPORT.md`  
- Resume: `release:check -- --resume` after bounded failure  

### Stage structure
- Explicit dependency barriers between typecheck, API shards, browser.  
- API shards: max parallelism capped; each shard serialized internally; time limits.  
- Browser stages strictly serial.

### Risks / gaps
- Evidence can rot if agents treat green CI unit tests as “release ready.”  
- Full suite cost means local full checks are rare—regressions may surface late.  
- Revision binding prevents swapping an old PASS report onto a new SHA.

## 10. How these systems connect

```text
Import apply → factory KV / profiles / recipes
       ↓
Factory + profile sync (stamp KV)  ←→  SSE config invalidation nudge
       ↓
Operator opens run → profile defaults copy into runValues
       ↓
live-calc computeCalc / server computeServerCalc
       ↓
auto-track schedule → claims → mutations on runValues
       ↓
day-state sync (partial/complete) + protectRunValues
       ↓
SSE live projection (calc ticks, coordination)
       ↓
(optional) inventory consumption on claim
```

Home composes all client sides; release evidence proves critical paths still work together.
