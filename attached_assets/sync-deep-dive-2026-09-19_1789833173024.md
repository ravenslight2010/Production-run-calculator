## 1. Architecture at a glance

```text
┌─────────────────────────────────────────────────────────────────┐
│ Browser tab (one sync owner)                                      │
│  SynchronizationStateMachine: connecting → ready → pushing       │
│                         ↘ waking / resetting                      │
│  syncPushQueue: single-flight PUT; newer local state replaces queue│
│  runSyncPolicy: blank/tombstone/stamp rules (pure domain)        │
│  operational-intent outbox: pause/resume/end/corrections (idempotent IDs) │
└───────────────────────────────┬─────────────────────────────────┘
                                │ PUT /sync/today | /sync/:date
                                │ GET /sync/events (SSE)
                                │ POST operational intents
┌───────────────────────────────▼─────────────────────────────────┐
│ API                                                             │
│  Reset epoch FOR UPDATE → daily_sync FOR UPDATE                 │
│  Partial? validate baseSnapshotId under lock → inherit omitted │
│  protectRunValues → capMergedResult → write                     │
│  detectConflicts (outside txn) → broadcast SSE (complete frames)│
│  Live calc ticks from client.lastData cache                     │
└─────────────────────────────────────────────────────────────────┘
```

**Ownership (from storage-sync-ownership):**  
Home owns canonical live `DayState`; the state machine owns connection/push/wake/reset ordering; pure domain owns merge policy; server owns protected merge inside the locked transaction.

## 2. Wire identity & contracts

### 2.1 Snapshot ID

```ts
// lib/syncContract.ts
syncSnapshotId(data) = sha256(canonicalSyncJson(data))
// key-order-independent object walk
```

- Query/header style short-circuit: if client’s `snapshot` matches, respond `{ unchanged: true, snapshotId }` without re-sending the body.
- Partial writes **must** carry `baseSnapshotId` matching the locked row’s snapshot or they are rejected.

### 2.2 Completeness

| Mode | Marker | Meaning |
|------|--------|---------|
| Complete | `completeness: "complete"` (default responses) | Full document; required for initial adopt & recovery |
| Partial | `completeness: "partial"`, `syncVersion: 1`, `baseSnapshotId` | Hot write may omit unchanged run values / cold sections |

**Partial contract validation (`isValidPartialSyncContract`):**

- `syncVersion === 1`
- `baseSnapshotId` matches `/^[a-f0-9]{64}$/`

**On invalid/stale base (under row lock):**

- **Do not apply** the delta  
- Return complete authoritative snapshot  
- `partialFallback: true`  
- Response header `X-Sync-Response: partial-fallback`

Institutional rule: *A missing, malformed, stale, or raced dependency returns the complete authoritative snapshot without applying or broadcasting the delta.*

### 2.3 Size limits (recap)

| Layer | Limit |
|-------|--------|
| Express parser | 10mb |
| Sanitized aggregate | **512 KB** (`MAX_AGGREGATE_BYTES`) |
| Runs | 50 |
| List entries / string len | 500 / 200 |

Large-day integration tests already compare **complete vs partial** PUT wire bytes for a representative 32-run day.

## 3. Server write path (detail)

### 3.1 Partial merge under lock

```text
FOR UPDATE daily_sync
canonicalExisting = completeSyncData(existing)
if partial:
  if !valid contract OR baseSnapshotId !== syncSnapshotId(canonicalExisting):
    return { wrote: false, partialFallback: true, data: canonicalExisting }
  payloadForMerge = { ...canonicalExisting, ...payload }  // inherit omitted cold sections
else:
  payloadForMerge = payload

serverOwned = capPackagingManualOverrideUntil(payloadForMerge, serverTime)  // ≤ +60s
merged = protectRunValues(serverOwned, canonicalExisting, {
  allowRunListReplacement: date > clientTodayDate  // future scheduled only
})
capMergedResult → canonicalizePepNames → applyResetBoundary → UPDATE/INSERT
```

**Critical property:** Partial validation runs **while the row lock is held**, so another writer cannot change the base between check and merge.

### 3.2 What partial is *not*

- Not RFC 6902 JSON Patch  
- Not field-level ops (`replace /runValues/x/casesNeeded`)  
- Coarse: “here is a sparse document; inherit the rest from the locked snapshot, then run full LWW protection”

### 3.3 Conflict detection (observability)

After successful write (outside transaction):

`detectConflicts(incoming, existing, merged)` compares canonical JSON for:

- `runValues:{id}` changed vs client intent  
- `packagingProgress:{id}`  
- `dayState.runs.meta:{id}`  
- `dayState.runs:appended(n)`

Logged to `syncConflictLogsTable` for trends (`SyncConflictStatsCard`). Does **not** change merge outcome—merge already happened via protect rules.

### 3.4 Broadcast

```ts
// Peers only: same scope + watchDate, exclude senderId
client.lastData = data;
client.lastCanonicalRevision = canonicalRevision;
res.write(complete frame including liveState);
```

- Broadcast frames are **`completeness: "complete"`** today (full document to peers).  
- Calc ticks use updated `lastData` without re-reading DB.  
- Master-data changes use a **separate nudge** (`configurationInvalidated` + small family enum)—not the full recipe payload.

## 4. Protect merge (behavioral core)

Documented extensively in `protectRunValues.ts` header. Summary for sync design:

| Concern | Behavior |
|---------|----------|
| Run values | Per-run LWW on `runValuesUpdatedAt`; equal/older stamp keeps stored |
| Blank over populated | Exact deep-equal to blank templates → refuse overwrite |
| Run list | Union by id; tombstones from either side; no silent drop |
| Today vs future | Today never allows run-list replacement via client resetAt |
| Daily reset | Incoming `resetAt` strictly newer → wholesale adopt |
| History | Omitted on push → preserve server history |
| Delete/undelete stamps | Max-merge maps; stale clients cannot strip |
| Auto-track coordination | Invalidated when progress registers change |

Client mirrors blank protection in `domain/runSyncPolicy` / blank-run tests.

## 5. Client sync owner

### 5.1 State machine phases

| Phase | Meaning |
|-------|---------|
| `connecting` | No baseline yet; pushes deferred |
| `ready` | Initial snapshot adopted; may push |
| `pushing` | Exactly one PUT/retry chain |
| `waking` | Must pull+adopt before publish (focus/visibility/online) |
| `resetting` | Generation bump; cancel older work; empty baseline |

**Rules:**

- Baseline before push (`completeInitialSnapshot`)  
- Single-flight: concurrent edits **replace** queued snapshot (latest wins locally)  
- Wake generation must match to acknowledge  
- HTTP 200 is not ack until response classified: stale epoch / canonical adopt / unchanged snapshot / terminal failure

### 5.2 Push queue

One in-flight PUT per tab; local edits during flight replace the queued request so the next write uses the newest snapshot.

### 5.3 Wake guard

`foregroundSyncWakeGuard` coalesces focus/visibility/online bursts into one shared reconciliation promise.

### 5.4 Operational intents (parallel path)

Not the same as day-state PUT:

- Browser outbox with durable pending/sending records  
- Server `operationalIntentLedgerTable` — **idempotent by intent id**  
- Same reset-epoch + document lock ordering  
- Duplicate delivery returns **original** snapshot/outcome (timeout-safe)  
- Failure matrix documented (auth, reset mid-flight, 403, corruption, etc.)

Use intents for lifecycle/corrections; use day-state PUT for form/setup bulk state.

## 6. SSE live channel

| Mechanism | Behavior |
|-----------|----------|
| Initial frame | Always (even empty day); sets baseline |
| Heartbeat | ~15s (`AUTO_TRACK_HEARTBEAT_MS`); may include auto-track schedule |
| Calc tick | ≥2s (`LIVE_CALC_TICK_MS`); from `lastData` cache |
| Day broadcast | Complete document + liveState to same-day peers |
| Config invalidation | Bounded family nudge; sender excluded |

**Implication for “delta SSE”:** Peers still receive full documents on every write. Partial PUT saves **upload** bytes; **download** to other tablets is still complete. Next optimization after partial PUT: revision-keyed patch or “unchanged sections” on broadcast (harder; every peer’s last revision may differ).

## 8. What “improve sync” means now (revised)

Earlier roadmap language (“add delta sync”) understated the system. Revised backlog:

| Already built | Still missing / weak |
|---------------|----------------------|
| Partial PUT (`completeness: partial` + `baseSnapshotId`) | Broader partial sections (not only run-values omission) |
| Snapshot unchanged short-circuit | JSON Patch optional path (finer than whole-run omit) |
| LWW + blank + tombstone guards | SSE **outbound** compression / patch frames |
| Offline push coalescing + wake fence | Per-device last-seen / queue depth for managers |
| Conflict **logging** + stats UI | Conflict **visibility toast** when client lost fields |
| Operational intent ledger | — |
| 512 KB app cap + sanitize | Metrics of real p50/p95 put sizes |
| Heartbeat + calc ticks | Proxy buffering off; multi-instance bus if scaled |

### Recommended next steps (ordered)

1. **Measure** partial vs complete adoption in production (how often `X-Sync-Response: partial-fallback`?).  
2. **Expand partial** only for proven hot paths (progress registers) while keeping complete recovery.  
3. **Optional JSON Patch** as an alternate encoding of the same “base snapshot + delta” idea—still validate base under lock, still run `protectRunValues` on the reconstructed full doc.  
4. **SSE outbound** optimization second (peer bandwidth).  
5. **Device health** surface using existing conflict stats + last successful sync timestamps.

## 9. Invariants checklist (do not break)

From memory + code—any sync PR must preserve:

1. Client-local date on every endpoint  
2. Reset epochs fail closed  
3. Compatible lock order: reset fence → document (and intents)  
4. Tombstones and delete/undelete stamps survive stale clients  
5. Separate LWW stamps for run meta vs run values  
6. Blank-over-populated rejected client **and** server  
7. Wake: adopt before publish / counter advance  
8. Completed history survives live-day reset  
9. Partial never applied on snapshot mismatch  
10. Canonical responses for initial adopt remain **complete**  
11. Conflict logging never rolls back a successful write  
12. Packaging manual override capped by **server** clock (+60s)
