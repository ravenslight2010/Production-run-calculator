## 2. Strengths (keep)

1. **Protective merge (`protectRunValues`)** — Additive run-list union, per-run stamp LWW, blank-over-populated guard, reset wholesale adopt, history retain-on-omit, delete/undelete stamps. Unusually mature for a custom facility API.
2. **Server live projection** — Calc/timers/phases computed server-side and streamed; clients adopt with freshness windows.
3. **Health probe design** — Liveness (`/livez`) independent of DB/AI; readiness includes startup phase, DB `SELECT 1`, AI config, background worker degradation.
4. **Sync health sentinel** — `buildSyncHealthReport` is read-only, redacted, and explicitly does not auto-repair (correct ops posture).
5. **AI resilience primitives** — Exponential backoff + jitter, retryable classification (429/5xx/timeouts), circuit breaker class.
6. **Test surface** — Dedicated release shards for sync, SSE, roles, concurrency under pool pressure.
7. **Body-limit lesson captured** — 10mb stopgap documented; structural fix preferred over endless raises.

## 3. Research by server concern

### 3.1 Sync write path & concurrency

**Today:** Full-document PUT; `canonicalRevision` as version; protective merge; SSE notify peers.

**Industry patterns:**
- Optimistic concurrency via version / ETag / `If-Match` (reject or merge on mismatch)
- JSON Patch (RFC 6902) with optional `test` op on revision before apply
- On conflict: return 409 + current document, or server-merge and return new revision (this app’s style)

**Research takeaways:**
| Topic | Recommendation |
|-------|----------------|
| Delta body | Accept optional JSON Patch; reconstruct full candidate; **then** `protectRunValues` (never patch inside the guard) |
| Library | `fast-json-patch` for compare/apply (see further-research §8.3) |
| Revision | Keep `canonicalRevision` as shadow key; optional `If-Match` / body `baseRevision` for strict clients |
| Reset | Continue wholesale adopt when `resetAt` advances—do not patch across reset |
| Metrics | Log `sync.put.bytes`, `sync.put.runs`, `sync.sse.frame_bytes` (sampled) |

**Risk:** Patch apply bugs → always fall back to full state (already in sync plan).

---

### 3.2 SSE (Server-Sent Events)

**Today:** `GET` sync events stream; broadcast on accepted writes / master-data / reset / rollover; live calc ticks on same channel.

**Industry practices:**
- Headers: `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`, `X-Accel-Buffering: no` (disable nginx buffering)
- Heartbeats/comments to keep intermediaries from closing idle streams
- Track clients in a `Set`; remove on `req.close`
- **Connection cost:** each SSE holds a server socket; at multi-instance scale, need sticky sessions or a pub/sub bus (Redis, Postgres LISTEN/NOTIFY)
- Browser limit ~6 SSE connections per origin (HTTP/1.1)—relevant if many tabs per tablet

**Research takeaways for this deployment scale (single facility, few tablets):**
- In-process broadcast is **appropriate** (do not require Redis yet)
- Document proxy timeouts (Render/Caddy) so long-lived SSE is not killed silently
- On multi-instance deploy later: Postgres `LISTEN/NOTIFY` or Redis hub to fan out—only when second API replica exists
- Prefer **patch frames** relative to last-acked revision once delta sync lands; full snapshot on connect/gap
- Heartbeat interval + client reconnect with `Last-Event-ID` if event IDs are introduced

### 3.3 PostgreSQL pool & query discipline

**Industry defaults (`pg` Pool):**
- `max` sized to DB `max_connections` / instance count (often 10–20 per small API)
- `connectionTimeoutMillis`, `idleTimeoutMillis`, `statement_timeout`
- `keepAlive: true` against idle TCP kills (LB / some hosts)
- `pool.query` for one-shots; `pool.connect` + `release` only for transactions
- Never hold a pool client across an SSE lifetime

**Research takeaways:**
- Confirm pool settings live in `@workspace/db` match host limits (Render Postgres plan)
- Sync PUT should be **short transactions**: read row → merge → write revision → commit → then broadcast (broadcast outside the transaction)
- SSE must not check out a dedicated DB client per subscriber
- Existing concurrency tests under “pool pressure” are the right soak class—extend for patch fallback

**LISTEN/NOTIFY note:** Useful for multi-instance SSE fanout later; requires session-mode pooling (not transaction pooling) for listen connections.

### 3.4 Health, readiness, and degradation

**Today:**
- `/livez` — process up
- `/readyz` `/healthz` `/` — startup gate + DB + AI keys + background workers
- Sync health report separate (canonical doc / revision / projection / command history)

**Industry split:** Liveness ≠ readiness ≠ deep dependency checks. Don’t mark unready solely because optional AI is missing if floor ops must continue—**product decision**.

**Research takeaways:**
| Check | Suggestion |
|-------|------------|
| AI missing | Consider **degraded** vs **not ready**—floor sync should work without AI keys |
| Background workers | Keep failing readiness on *sustained* failure (already modeled) |
| Sync health | Expose manager-facing; do not block `/readyz` on projection mismatch |
| Payload | Optional gauge: p95 body size last N puts (ops, not readiness) |

---

### 3.5 Auth, rate limits, session boundary

**Today:** Staff signup code, manager bootstrap, capability routes, auth rate limits, `sessionBoundary` at facility-local reset.

**Research takeaways:**
- Daily reset fence is correct for shared tablets—keep server clock / facility timezone single source (`facilityTime`)
- Rate-limit auth aggressively; sync writes by user/device more carefully (avoid blocking legitimate multi-tablet bursts—concurrency tests exist)
- Future device-health endpoint should be **authenticated** and scoped; no document bodies in responses (mirror syncHealth redaction)

---

### 3.6 AI routes on the server

**Today:** Many `ai*` routes; shared retry/circuit breaker; cost limit telemetry; result cache patterns; retention policy docs.

**Research takeaways:**
- Keep AI failures isolated: circuit open must not stall sync or health liveness
- Bound request body and output tokens; prefer deterministic import path (importer redesign)
- Server-side **timeouts** on upstream GenAI calls shorter than client HTTP timeout
- Portfolio cleanup is product policy (value audit)—server enforces by not exposing retired routes

---

### 3.7 Background jobs & data heals

**Today:** `serverJobs`, background operations diagnostics, extensive heal/repair registry (ingredient, brand, mix, source library, etc.).

**Research takeaways:**
- Heals are powerful—treat as **break-glass** with audit logs and fingerprints (already partially present)
- Job runner should be single-flight per job type where possible (avoid duplicate heavy repairs)
- Surface job degradation on readiness only when jobs are load-bearing for startup

**Today:** Pino + pino-http; correlation on health; observability helpers; cost telemetry for AI.

---

### 3.9 Deploy topology

**Today:** Slim API image vs migrate image; forward-only schema; Render-style host; Caddy in compose.

**Research takeaways:**
- Single API instance is fine for current scale; design SSE broadcast as **interface** so a later Redis/NOTIFY adapter can plug in
- Proxy: disable buffering for `/api/sync/events`
- Graceful shutdown: stop accepting new SSE, drain short PUTs, release pool
- Schema rollback policy already rehearsed—keep code-only rollback discipline

## 5. Explicit non-goals (server)

- Replacing PostgreSQL with a document DB for day-state  
- Event-sourcing the entire day-state in the same project as delta sync  
- Moving live calc back to pure client authority  
- WebSocket rewrite of SSE without a measured need (SSE fits one-way projection + notify)  
- Auto-repair from sync-health checks (sentinel must stay read-only)
