# Candidate Toolchain Browser Release Blockers

**Date:** 2026-10-05  
**Decision:** Reproduce the browser failures on the current source tree, make only
the smallest fixes supported by those reproductions, then rerun candidate
validation.

## Context

The candidate is Node 24.21.0 with pnpm 12.8.1. The lockfile SHA-256 is
`46e0a8324425303ce157f10f8412caf0c3e22b81c7c22ab8df5143569d7e4f88`.

The full candidate run completed its browser inventory but failed three browser
gates: accessibility, phone/tablet WebKit compatibility, and the full E2E suite.
The E2E suite passed 168 of 170 cases. The browser report is bound to
`test-sha256:7360d8d5abb9109b80043a76f404dbcb10717d61e798f1a50652835a61eb7e7f`.
After that run, the current source advanced to commit
`011b3028e36af2cefc0424fb2fd1e15204ff365e`; the lockfile hash did not change.
That merge changed the stoppage-log button from `text-orange-800` to
`text-orange-900`, so the contrast failure must first be checked again on the
current tree.

The checked-in `release-evidence-full/release-check-report.md` is stale. The
failed run wrote a current release-state checkpoint and a full-browser report,
but it did not produce a successful final release report. Its disposable
environment also skipped production source-library reconciliation; it is not
production evidence.

## Failures in the prior browser report

1. **Phone accessibility contrast:** the stoppage-log “Log Stop” button was
   measured at 3.56:1 (`#b97725` on `#fbfcfd`; 4.5:1 required). Recheck after
   the merged color change. If it still fails, use a foreground color that
   meets the threshold in the light theme while preserving the dark-theme
   treatment.
2. **Tablet WebKit disclosure:** clicking the native report `<summary>` did not
   set the enclosing `<details open>` state. Reproduce before changing markup
   or test interaction; retain native disclosure and keyboard behavior.
3. **Mix recipe refresh:** after editing a shared mix recipe, the pending-run
   Ingredient Detail did not change before the 20-second assertion timed out.
   Dough, sauce, and cheese variants passed. Trace the mix update through the
   canonical pending-run value and peer refresh. Started-run snapshots must
   remain frozen, and asynchronous updates must stay bound to their originating
   run.
4. **Offline wake counter setup:** before the wake scenario began, the dough
   setup helper expected 2 batches but observed 3 for 15 seconds. Determine
   whether the mismatch is test setup timing or a product counter defect. Do not
   add a fixed delay, clamp a counter, or change dough math without evidence.
   Preserve the wake reconciliation acknowledgment and post-wake counter rebase.

## Approaches

- **Reproduce first, then make evidence-based minimal changes (selected):** run
  only the four failed cases against a clean disposable database on the current
  candidate runtime. Fix only failures that reproduce, at the component, sync
  path, or test setup where the evidence places the defect. This avoids changing
  correct behavior to satisfy a stale or timing-sensitive test.
- **Patch from the prior run immediately:** faster, but risks changing app
  behavior to mask a test or fixture problem.
- **Stop at the current NO-GO:** no app changes, but the requested toolchain
  qualification remains incomplete.

## Boundaries

- Do not change Node, pnpm, TypeScript, `minimumReleaseAge`, or security
  overrides as part of these browser fixes.
- Do not refactor sync broadly or alter unrelated recipe, dough, timer, or
  accessibility behavior.
- Change a test instead of product code only when current product behavior is
  shown to meet the contract and the test setup/assertion is the cause.
- For wake changes, preserve the adopt-before-publish barrier, canonical
  acknowledgment, and one-time counter rebase. Run both sync-invariant and
  state-accuracy checks if sync or counter behavior changes.

## Verification and evidence

1. Focused isolated browser reruns for the phone accessibility case, tablet
   WebKit report disclosure, mix refresh case, and offline-wake counter case.
2. Focused package/unit checks for each modified path; include the sync/wake
   regression set if that behavior changes.
3. Rerun the complete candidate release check on the final source tree with
   Node 24.21.0 and pnpm 12.8.1. Accept evidence only when the full report is
   generated by that successful run and binds to the tested source and
   unchanged lockfile.
4. Keep the disposable run separate from production reconciliation evidence.
