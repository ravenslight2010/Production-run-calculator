---
name: Wake sync claim fence
description: Foreground wake auto-track claims must wait for a monotonic reconciliation acknowledgment without deadlocking same-tick dough claims.
---

The foreground reconciliation acknowledgment is the safe boundary for resuming automatic production claims. It must be monotonic and distinguish the current wake from a stale recovery notice; once that boundary has passed, queued claims from the same visible cadence must not wait on the local sync write generated by an earlier claim.

Reconnect recovery has two independent transports: the SSE baseline and the date-scoped HTTP pull. They must share one owner and one publish fence. A full canonical pull is adoptable only when its client date, complete run/value correspondence, and server snapshot digest all validate; malformed or superseded responses must mutate no canonical refs.

Partial payloads are a write optimization only. After the server merges one, the stored and returned canonical document must be normalized back to a complete contract with a digest computed from that complete document.

**Why:** A screen wake can release the UI fence and trigger a dough cadence in the same React render. A fixed timeout either drops valid claims or allows stale hidden-time claims, while waiting on every subsequent local push can serialize away the second claim in the same tick. During reconnect, either transport can win the race; testing only the HTTP failure can accidentally pass through SSE and never exercise the fenced failure state. Retaining a partial marker after merge makes an otherwise complete recovery response fail closed forever.

**How to apply:** Keep the browser evidence tied to the acknowledgment attribute and assert the actual claim channels plus persisted counters. Preserve the production fence before acknowledgment; after acknowledgment, let the server-side claim base/rebase logic handle the queued same-tick mutations. Recovery failure tests must block both SSE and HTTP until retry.
