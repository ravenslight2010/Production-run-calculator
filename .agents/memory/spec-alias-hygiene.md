# Spec-import alias hygiene

Rules (all enforced in `@workspace/spec-import` `sanitizeSpecAliases`, applied on EVERY alias read/apply path — canonicalize, blend alias application, premix redirects):

- **Digit-signature mismatch aliases are dropped** for brand/flavor/appType/pepType: an alias whose external and canonical names have different digit signatures (e.g. `"11 IN FOUR HANDS" → "Four Hands"`, `Lowe's 7" → Lowe's`) is never applied. Names differing by digits are DIFFERENT products; this is the fix for the Lowe's vs Lowe's 7" brand collapse.
- **Generic slot-type names** ("Mix"/"cheese") are rejected on either side of appType aliases.
- **Cross-family mix↔cheese appType pairs are never applied or learned** (`isCrossFamilyMixCheesePair`): an appType alias whose two names fall in different families — cheese-token names ("...Cheese Mix", cheese-word wins over mix-word) vs plain mix-token names — silently re-routed a MIX applicator onto a cheese recipe on every re-import (the Bobo Breakfast Mix incident). Neutral names ("...Blend") never trip the guard; `recipeName` kind is exempt (explicit user review). Guarded at sanitize, the `applyNameMatches` appType learn loop, and the server POST backstop. Poison undone by heal `bobo-cross-family-alias-undo-v1` (re-runs sanitize purge per scope, deletes mirrored ai_corrections, restores verbatim applicator names in saved parses).
- **Chains/cycles** (a name that is both alias source and target) are removed.
- **Modifier-dropping (token-subset) pairs are dropped for INGREDIENT kinds** (cheese/dough/sauceIngredient): if one name's loose-key token set is a proper subset of the other's (`"Sea Salt" → "Salt"`), the alias is never applied or learned (`isModifierDropNamePair`). Ingredient aliases auto-apply with no review step, so a subset pair silently rewrote different ingredients as one. Guarded at sanitize, `applyNameMatches` apply+learn, and both server POSTs (/spec-import-aliases for ingredient kinds, /ai-corrections for domain "ingredient"). brand/flavor/appType/recipeName are exempt — their renames come from explicit user review ("Cheeseburger Cheese Mix" → "Cheeseburger Mix" is a deliberate pick). Typos are safe: they alter a token, not remove one. Poisoned rows undone by heal `sea-salt-alias-undo-v1` (deletes the pair by normalized names all scopes; renames pool rows back only where the SOURCE sheet says Sea Salt and the stored amount matches the sheet or is a 0 stub — see api-server `seaSaltHeal.ts`).
- **Fuzzy matches are NEVER learned** (`collectSpecAliases` skips `source === "fuzzy"`): unconfirmed fuzzy guesses written to factory-wide memory were the root cause of poison aliases. Only user-confirmed renames and applied aliases are learned.

**Why:** learned aliases are factory-wide and permanent — one bad fuzzy guess silently rewrote every future import (brand collapse, cross-brand Red Hot mix confusion).

**How to apply:**
- Any NEW code path that reads/applies spec aliases must go through `sanitizeSpecAliases` (it preserves survivor object identity, so `Set` membership works for drop detection).
- An explicit user rename that drops/changes digits (e.g. renaming "Four Hands 11" → "Four Hands") will be learned but BLOCKED at apply time by the digit guard — this is intentional; tests lock it in.
- Rows themselves were purged once via the marker-guarded heal `spec-alias-hygiene-purge-v1` in api-server dataHeals (per-scope grouping so chain detection only sees aliases applied together). If the sanitize rules tighten again, ship a new heal id — old markers won't re-run. `generic-mix-poison-purge-v2` re-ran the purge after new poison landed (see below) and also removed poisoned `ai_corrections` item rows + garbage/junk mix records.
- **Sanitizing at APPLY time is not enough — every alias CONSUMER and LEARN path must sanitize too.** Poison re-accumulated after v1 because the review dialog's pre-selected "Use existing" picks (`buildAliasLinkSuggestions`) read the RAW alias list, then the confirmed pick was re-learned — a self-perpetuating loop that renamed every blend to the literal "Mix" and merged them into one garbage record. Now fixed at four layers: suggestion build sanitizes first, the learn path skips generic names, the commit save filters via `sanitizeSpecAliases`, and the server POST /spec-import-aliases route rejects generic appType rows outright (backstop for old clients). cheese-import's `buildCheeseAliasLinkMap` has its own local generic-name guard (package stays dependency-free).
- **Deleted names must be excluded from the import match universe AND from alias targets.** The digit guard folds number WORDS to digits ("four"→"4"), so a renamed flavor ("4 Cheese Meltdown") legally matches a deleted old one ("FOUR CHEESE MELTDOWN") — the import then lands under tombstoned names the user can't see and autofill finds nothing. Fix: the known-lists glue filters brands/flavors through the deletion tombstones (stamp-arbitrated), and fetched aliases whose canonical brand/flavor is deleted are dropped before use. Any fix like this needs a SPEC_PARSE_VERSION bump — saved parses have the bad grounding baked in.
